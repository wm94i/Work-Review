# Windows 桌宠亮屏黑块回归（#190）

## 修复范围

针对已有桌宠窗口的 Windows 原生透明合成状态丢失：复用当前会话亮屏／恢复通知，延迟 250ms 合并相邻通知，在 GUI 线程重新应用与 Tao 创建窗口相同的 DWM 透明参数。平时没有额外轮询。

- 熄屏、进入待机、仅变暗或重复亮屏不会触发恢复；后台唤醒但会话仍熄屏时也跳过。
- 执行前再次检查显示状态和窗口是否可见；不创建窗口、不重新显示已关闭的桌宠。
- 用户重新开启桌宠时也请求一次恢复，覆盖其隐藏期间发生的状态丢失。
- 录制暂停、截图关闭、主界面隐藏均不影响电源回调；不依赖采集循环是否正在记录。
- 不重建 WebView、不改变位置／尺寸／鼠标穿透、不抢焦点、不重置通知和专注状态；保留原有气泡样式和硬件加速。
- Windows API 失败记录日志，临时 GDI 区域始终释放，不无限重试。
- 不改变 #189 的活动分段规则，不修改数据库或历史记录。

## 原生故障注入验收

只操作独立测试程序自己的 HWND，不关闭整机 DWM、不重置系统显卡驱动，不读取正式工作记录。测试程序使用项目相同的锁定依赖，并直接编译生产恢复模块。

1. 透明通知窗口放在已知纯色测试背景上，记录边界、窗口扩展样式、前台焦点、消息内容和 WebView2 背景 alpha。
2. 仅对该窗口取消 DWM 透明状态，确认外围出现黑矩形、气泡内容仍存在。
3. 触发生产恢复路径，检查外围重新透出已知背景；重复调用应幂等。
4. 分别在鼠标穿透开启和关闭时重复；不得改变 `WS_EX_TRANSPARENT`／`WS_EX_LAYERED`、位置、尺寸或前台焦点。
5. 合并一批相邻通知，只执行一次恢复；恢复排队后关闭桌宠，不能重新显示。重新开启时能够恢复。
6. 在显示关闭期间发恢复请求应跳过，后续亮屏再恢复；核对原生回调使用同一路径。

诊断阶段已确认：注入原生透明状态丢失会产生与 #190 附图相同形态的黑底；刷新 DOM、移除 CSS 模糊、隐藏／显示和调整尺寸不能恢复，而重施 DWM 参数可以恢复。WebView2 的背景 alpha 全程为零。

**故障注入不是实际熄屏复现。** 此结果支持修复原生透明状态恢复缺口，不能证明报告者的具体显卡／驱动触发原因。

## 实际熄屏／待机验收（需用户主动操作）

在隔离数据环境运行包含修复的新构建，记录 Windows、WebView2、显卡驱动版本和屏幕缩放比例。由用户手动熄屏／唤醒，不改电源策略：

- 普通熄屏再亮屏，以及睡眠／待机再唤醒，各重复数次。
- 桌宠本体显示／隐藏（仅通知）各一轮；鼠标穿透开启／关闭各一轮。
- 分别覆盖有气泡、没有气泡、持久提醒；恢复后消息不被清掉，交互按钮正常。
- 暂停录制、主窗口隐藏时仍应恢复；桌宠关闭时不能自行出现。
- 多屏／不同 DPI 环境确认位置尺寸不变，焦点不被抢走。

通过条件：不残留黑矩形，透明区域正确透出桌面，原消息、焦点、位置和鼠标穿透不变，无持续恢复循环或新增 CPU 唤醒。若失败，提供时间、版本和日志中的“恢复桌宠原生透明失败”／“调度桌宠透明恢复失败”；无需上传整个数据库或工作截图。

未经实际设备确认，不以自动测试或故障注入结果代替实机验收，也不直接关闭 #190 或相关的 #177。
